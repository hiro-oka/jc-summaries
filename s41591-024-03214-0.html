🏥 聖路加ICUでの実践への示唆

聖路加ICUでの実践

JIPAD × DPC 連結にこの枠組みをどう使うか ① 「連結したあと何をするか」の解析基盤が、本論文でそのまま埋まる。 ★JIPAD Home にある通り、JIPAD×DPC連結アプリは2025年に開発完了し、5施設パイロット（広島大・堺市立総合医療センター・弘前大・聖路加・東北大）のデータ収集が終わって処理中。次に来るのが ICU質指標の自動算出 だが、「連結したテーブルをどの構造に置き、どの手順で品質管理し、どうやって結果を他施設と共有するか」は未定義。ehrapy はその空白を埋める既製の答えを提示している。しかも 重症治療のデータ共有・ハーモナイゼーション24原則 — SCCM Data Science Campaignの系統的レビューと修正Delphi（CCM2025） が「原則」として言葉で示したもの（共通データモデル、メタデータとprovenance、データ品質の限界の透明な文書化、FAIR）を、動くコードに落としたものとして読める。SCCM原則＝WHAT、ehrapy＝HOW という対応。

② データモデルは OMOP CDM を入口に、実体は AnnData に置く。 ehrapy の入出力モジュールは OMOP・CSV・SQL データベース（Pandas経由）のリーダを持ち、読み込むと AnnData（h5ad / Zarr） オブジェクトになる。AnnData は X（データ行列）・obs（患者/入室単位のメタデータ）・var（変数側のメタデータ、欠測率など）・obsm/varm（PCA・UMAP等の埋め込み）・obsp（患者間の連結行列）・uns（非構造メタデータ）を次元を常に揃えたまま1ファイルに同梱する。JIPAD側の入室情報を obs、DPC側の診療行為・病名・コストを変数として X/layers に載せる設計が素直。「行＝入室（visit）、列＝測定量」という ehrapy の規約は、JIPADの1入室1レコードとそのまま一致する。標準としては OMOP CDM・HL7・FHIR・openEHR と互換と明記されている。

③ 再現性の担保方法まで具体的に真似できる。 著者らは解析本体（https://github.com/theislab/ehrapy ・Apache 2.0・PyPI配布）と再現用リポジトリを分離している：https://github.com/theislab/ehrapy-reproducibility に、図表を再現する Jupyter notebook と 全パッケージのバージョンを固定した Conda 環境定義 が入っている。JIPAD二次利用研究（40件超）で「どの解析コードで、どのバージョンで、どの前処理で出した数字か」を問われる場面が必ず来る。論文＝結果、別リポジトリ＝環境固定つきノートブックという二本立てを、JIPAD×DPCの最初の論文でそのまま採用したい。AnnData がプラットフォーム非依存に保存・読み出しできるため、中間生成物ごと共有できるのが従来のCSV+Rスクリプト運用との最大の差。

④ 「連結したら見えてしまうバイアス」を先に測る道具が入っている。 JIPAD×DPC連結は施設ごとに入力方式が違う（FileMaker手入力が残る施設あり＝★JIPAD Home 記載の課題）。ehrapy の CohortTracker（tableone + participant flow diagram）は、絞り込みのたびに集団の年齢・人種等の分布がどう動いたかを追跡して図にする。本論文の糖尿病130病院データの例では、Medicare受給者に絞った瞬間に60歳超へ分布が寄り白人比率が上がることを検出している。「除外基準を1つ足すたびに集団がどう歪むか」を figure にできるのは、多施設DBの限界を透明に書く（＝SCCM原則）ための実務的な武器。

⑤ 因果推論を「連結データの目玉」に据えられる。 DPC連結の価値は薬剤・処置・コストが入ること。ehrapy の causal モジュールは dowhy ベースで、①因果グラフの明示 →②推定可能性の同定 →③効果推定 →④反証（refutation）とsensitivity analysis の4段階を強制する。本論文では小児肺炎で薬剤クラス→ICU在室日数の因果効果を推定し、プラセボ処置・ランダム共通原因・未観測共通原因による反証を行っている。「連結できたので回帰しました」ではなく「因果グラフを描いて反証まで回しました」を最初から標準手順にする ことが、因果の言葉と関連の言葉をどう使い分けるか — 問いが因果なら causal language が必要（BMJ2026） とも整合する。

⑥ ただし当院/JIPADで採用する前の留保。 ehrapy は GPU非対応で、依存ライブラリ（NumPy/scikit-learn等）の制約をそのまま継承する。ベンチマークは UKB の 261変数×488,170 visit を 8スレッド1CPU・最大60GBメモリで回した規模で、JIPAD 64万例なら Dask のout-of-core実装が要る（チュートリアルでは 50,000患者×1,000変数のin-memory約2GB → out-of-core 200MB未満）。筆頭著者の所属企業製ライブラリ（Bionty）依存という COI も踏まえ、「JIPADの正式基盤」ではなく「二次利用解析の推奨ツールチェーンの一案」として提案するのが現実的。

🧭 この論文の位置づけ（Known / Unknown / What's new）

内容
Known（既知）医療のデジタル化でEHRの大規模蓄積は常態化した。EHRデータから疾患予測・集団健康・最適治療方針・臨床試験シミュレーション・患者層別化ができることは示されてきた。一方でEHRは非標準フォーマット（HL7・FHIR、CSV/XML/JSON/RDB）に散らばり、選択バイアス・フィルタリングバイアス・サーベイランスバイアス・情報/コーディングバイアス・脱落/交絡バイアス、そして MCAR/MAR/MNAR の欠測に晒される。オミクス分野には Bioconductor や scverse という共同体標準があるが、EHRには無い
Unknown（未解明）異種混在（デモグラ・検査・バイタル・診断・薬剤・画像・自由文・オミクス）のEHRを、探索的に扱える拡張可能な共通基盤が存在しない。既存のEHR前処理ワークフローは、異種データ非対応・文書不足・パッケージ化されていない・探索的可視化ができない、のいずれかに該当し、多くはベンダー固有の商用解。結果としてEHRは特定の1つの研究設問のためだけに使われ、品質問題を抱えたまま機械学習に投入されがち
What's new（新規性）ehrapy（EHR Analysis in Python）を提示。単一細胞解析の AnnData 構造と scanpy を EHR に転用し、データ読込→品質管理→欠測補完→エンコード→正規化→統合→次元圧縮→クラスタリング→統計比較・生存解析・因果推論・軌跡推論まで 100以上の合成可能な関数を1つのオブジェクト上で回す。ベンダーロックインなし、Apache 2.0、20以上の公開EHRデータセット同梱。6つの実証（小児肺炎の層別化／肝酵素バイオマーカー×生存／薬剤クラス→在室日数の因果効果／UKBの心筋梗塞リスク多モダリティ予測／COVID-19胸部X線の擬似時間による重症度軌跡／糖尿病130病院データのバイアス検出と是正）で汎用性を示した

📌 全体要約

  • ehrapy は EHR・疫学データの探索的解析のためのモジュール式オープンソース Python フレームワーク。ベクトル化（構造化テーブル）できるデータならどのEHRにも適用できる。
  • 中核は AnnData。データ行列とその注釈（観測＝患者/入室、変数＝測定量）を常に次元を揃えて保持し、途中結果（PCA・UMAP・近傍グラフ・統計結果）をすべて同じオブジェクトに書き戻す。h5ad / Zarr でプラットフォーム非依存に保存・共有できる。
  • 6つのユースケースで実証：①PIC（中国・小児ICU）で「詳細不明の肺炎」を4群に層別化、②肝酵素（AST/ALT/GGT）を生存と紐づけてバイオマーカー化、③薬剤クラスのICU在室日数への因果効果を dowhy ベースで定量、④UK Biobank で心筋梗塞リスクを多モダリティ統合し C-index 0.81、⑤COVID-19 胸部X線 192枚を擬似時間で重症度軌跡に並べる、⑥糖尿病130病院10万件超で選択・サーベイランス・正規化・補完・予測の各バイアスを検出し Fairlearn で緩和。
  • 標準との互換：OMOP CDM・HL7・FHIR・openEHR、および一般的な表形式。オントロジーは Bionty 経由で Human Phenotype・Phecodes・Phenotype and Trait・Drug・Mondo・Human Disease に対応。自由文からの医学用語抽出は MedCAT。
  • 著者らの結論：ehrapy が EHR解析パイプラインを標準化し、EHR版「アトラス」やクエリ→参照マッピング、さらに医療基盤モデル（foundation model）の土台になる。将来は CELLxGENE / UCSC Cell Browser のような対話的EHRエクスプローラを構想。

4. ユースケース⑤：COVID-19 胸部X線の重症度軌跡

項目内容
データBrixIA データセット、192枚の胸部X線（放射線科医が6領域で採点した重症度アノテーション付き）

✅ Take home

  • ehrapy は、単一細胞解析で確立した AnnData ＋ scanpy の設計をEHRに移植した、探索的解析のためのオープンソースPython基盤（Nat Med 2024;30(11):3369-3380、Apache 2.0）。
  • 「行＝患者の入室（visit）、列＝測定量」＋注釈同梱という1つのオブジェクトに、品質管理・補完・正規化・統合・次元圧縮・クラスタリング・統計比較・生存解析・因果推論・軌跡推論を全部書き戻す。中間生成物ごと h5ad / Zarr で共有できるのが従来のCSV+スクリプト運用との最大の差。
  • 入口は OMOP CDM・CSV・SQL。標準としては OMOP CDM・HL7・FHIR・openEHR と互換を明記。オントロジーは Bionty（Human Phenotype／Phecodes／Drug／Mondo／Human Disease ほか）、自由文は MedCAT。
  • 再現性の担保は「本体リポジトリ」と「再現用リポジトリ」の二本立て。後者に Jupyter notebook ＋ 全バージョン固定の Conda 環境が入っている（theislab/ehrapy-reproducibility）。JIPAD×DPC の最初の論文でそのまま真似できる型。
  • バイアスを測る道具が標準装備：CohortTracker（フィルタごとの集団変化＋flow diagram）、Little's MCAR test、MissForest/MICE、bias検出関数、Fairlearn連携。「多施設DBの限界を透明に文書化する」という 重症治療のデータ共有・ハーモナイゼーション24原則 — SCCM Data Science Campaignの系統的レビューと修正Delphi（CCM2025） の原則を、実行可能な手順に落とせる。
  • 因果推論は dowhy ベースで「グラフ→同定→推定→反証」の4段が強制される。DPC連結で薬剤・処置・コストが入るJIPADにとって、これが最も価値の高いモジュール。
  • 留保：GPU非対応、大規模データは Dask のout-of-core前提、そして 筆頭著者がオントロジー基盤 Bionty を作る LaminLabs の従業員という COI。JIPADの「正式基盤」ではなく「二次利用解析の推奨ツールチェーンの一案」として扱うのが妥当。
